# 可恢复的紧凑新闻评分与缓存

目标：全量候选仍由AI评分，逐条保存正确结果，只修复失败条目；使用紧凑响应、按输入/输出预算组批、最多两路独立请求，避免一条引文错误使整批重算。重要性错误不丢弃已验证兴趣分。所有失败明确保留待评分，不用局部排名冒充全库排名。

新闻使用账号私有的应用层K/V：稳定内容指纹为K，标题摘要/标签特征、评分和已读结果为V；现有semantic_documents保存语义向量。它不是聊天模型内部逐层、逐token的Transformer KV张量，普通兼容API不提供此类张量下载。稳定Prompt前缀利于服务端缓存，但中转服务是否支持、命中多少以usage为准。

## 本次故障的可核实证据

本机报告的安全统计：350条候选，100条已评分、250条待评分；32次评分请求、13个失败批次、901.25秒、385750输入字符，正文阅读和解读调用均为0。旧日志没有保存每批具体校验字段，也没有usage，不能断言全部是引文问题，不能把输入字符当Token或推断服务商实际账单。

旧流程以整批覆盖/重要性引文校验作为一个闸门：一行错误导致20条一起重试，再失败则整批丢弃。全库评分不完整时不进入解读。这解释了“已经花费大量计算却只留下100条”，不是新闻数量被硬限制为100。

## 紧凑评分与可恢复调度

- prompts/interest_scoring_fast.md请求短数组：每行[id,兴趣分,[范围,影响,跨域,紧迫,持续],原文短引文]；无重要性依据为null。引文目标≤64字符，不输出理由、标题复述或逐条推理。不减少全库候选，不用向量或随机分伪装AI评分。
- 兼容原对象行和完整单一JSON围栏。逐条检查id唯一、整数分0—100；正确行立即保存，重复/非法id或非法分只影响自身。重要性单独验证：不合格则I未知并记录invalid_importance，合法兴趣分仍保存，不伪造重要性0分。旧式仅兴趣分仍兼容。
- 输出预算决定每批上限：有明确额度T时min(40,max(1,(T−512)//80))；无额度的兼容客户端32条；无settings的其他客户端20条。该估计不是精确token计数，不会擅自提高用户配置额度。
- 再按真实序列化输入字符预算递归分批，不为装下更多新闻而删掉确认兴趣。批次规划先完成，再按实际待评分批数B预留调用预算。
- OpenAICompatibleClient可fork独立请求状态，最多两路并发；其他客户端默认串行。计数/usage加锁，SQLite写入在调度主线程完成，避免并发诊断串台、重复计数和数据库竞争。
- 一个条目初次失败后最多补评两轮；只发送缺失条目、不附整批长草稿。输出不足、格式错误等缩小批次；有效结果不再传回模型重算。预算最多B+max(20,2B)次评分请求，另给最终K条保留11K次阅读/解读逻辑预算。HTTP重试另计。
- 401/403/404/400、429或未知请求错误停止派发；可识别传输/服务错误连续三次触发停止。已在途最多两路仍收尾并保存有效结果。不会为“必须完成”无限扣费、隐瞒故障或绕过用户停止操作。

即使最终还有极少数条目无法得到有效分数，也必须显示真实已完成/待处理数和原因；不将局部排名称为全库前N。下次“AI重新整理”只补剩余项，成功后按既有三个栏目选择、解读。背景线程取消在请求和批次边界检查；服务阻塞读取仍不保证立即取消，未增加新的等待时限。

## 新闻K/V、缓存失效与兼容

database/news_feature_cache.py管理两个账号私有表：

| 表 | Key | Value |
|---|---|---|
| news_feature_kv | 来源ID+规范URL+标题/前600字符摘要/日期/标签及版本的内容指纹 | 精简新闻特征，不复制长推理 |
| news_score_cache | 内容指纹+评分语义版本 | 已验证兴趣分、独立重要性版本/结果 |

同内容重新抓取或快照ID变化可复用决策；规范URL相同但内容变更不能沿用旧分。相同ID的内容改变会使当前分数/重要性/正文缓存失效，旧报告仍保留。旧版有效评分先导入应用缓存，保留原评分语义版本，不因只改变输出编码方式强迫整库重评；原interest_scoring.md继续用于语义量表版本兼容，实际请求使用fast文件。画像、问题或模型变化仍按原规则重评。账号查询全部检查归属，私密来源不借别的账号缓存。

semantic_text_vectors/semantic_documents继续保存文本及新闻/标签的384维编码；画像变动不要求把不变新闻重新embedding。这里的语义向量和应用K/V不是聊天模型的多层注意力KV张量，不保证中转站缓存命中。稳定系统指令和档案在请求前部、变化新闻在后部，JSON紧凑编码；不增添服务商未确认支持的cache/reasoning参数，不更换provider或模型。

## 解读与阅读复用

ResearchSession.resynthesize默认force_explanations=False：已有有效解读直接复用，失败/缺失或读者内容/正文变化才重做。调用方明确传True仍可强制重写。历史报告不被覆盖；重新整理生成新报告快照。

解读版本只取真正发送的reader_profile，不因档案内部版本号改变而失效；正文版本只取文本/状态/原因，不受抓取时间等附加元数据抖动影响。正文分段选取的缓存与写作风格分开：兴趣/问题/用途、相关阅读程度、模型、正文或阅读Prompt变化才使分段结果失效；仅改表达规则时复用已经校验的原文片段，再做一次新风格解读。短文仍直接读正文，长文仍覆盖全部块，不通过少读正文冒充节省。

## 用量与可观测性

客户端提取Chat/Responses的usage，包含已报告输入、输出、总Token、缓存输入和推理Token；推理是输出子集，缓存输入是输入子集，不重复相加。输出额度耗尽但返回usage的失败也计入。不存在usage仍为未知，不填0；HTTP失败/重试可能额外计费，报告统计不是完整账单。

BudgetModel记录usage_calls、usage_complete和token_usage，新闻报告另外记录scoring_reused、feature_cache_restored、scoring_workers、scoring_batch_limit、scoring_repaired_items、scoring_validation和scoring_failures。未完成原因只写安全诊断码，不存原始上游正文、私密Prompt或密钥。界面“检索详情”显示复用/补评数和已报告Token。

## 验证

项目虚拟环境运行tests/unit/test_efficient_scoring.py：350条控制案例中，故意让13个旧式批次含不匹配引文，旧校验仅保留100条，新路径保留350条兴趣分，I错误保留未知，生成10条解读。配置4096输出预算时评分9次、解读10次；再次整理0次新增模型请求。这是模拟响应，不证明真实网络耗时或真实兴趣质量。

另外覆盖：只补缺失行、围栏、重复/布尔分拒绝、输出不足分批、最多两路并发、主线程保存、认证/限流熔断、Token与失败计数、跨快照缓存和内容失效、账号隔离、小上下文预算规划、表达变化复用长文读取。相同合成结果的紧凑JSON字符数小于原对象形式40%，不是实际模型Token降幅保证。

参考[OpenAI延迟优化](https://developers.openai.com/api/docs/guides/latency-optimization)关于减少输出、稳定前缀、并行和传统缓存的建议；[提示缓存说明](https://developers.openai.com/api/docs/guides/prompt-caching)说明KV前缀复用和服务端用量指标。第三方服务支持情况需实测，不套用官方缓存折扣。
